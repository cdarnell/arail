{#- _boot_overlay.html — the cold-start "warming up" overlay. Included once from base.html's global_ui block, so it's present on every portal page (welcome.html is nav-less and deliberately excluded from base.html entirely — this doesn't apply to onboarding). Purely time-based: `boot_epoch_ms` (wall-clock ms) is stamped into every page from a plain Python global — see app.py, where it's re-stamped at the END of the startup handler (not at import) so the window is anchored to "the app can actually serve a request," not to raw import start; a real cold boot was measured taking ~10s just to reach that point, so anchoring any earlier would have left the whole budget already spent before any browser could load the first page. The client compares that stamp against its own Date.now() once, on load, and either shows the overlay for the remaining budget or does nothing at all. No fetch, no XHR, no polling, no repeated timers — a single comparison and exactly one setTimeout — deliberately not even a local setInterval for a ticking elapsed-time readout, since a recurring timer is still "an update happening post boot" in the literal sense the operator ruled out, even with zero network cost. This is deliberate: the lab's quiet-boot contract means nothing probes or checks readiness after boot unless the user asks, and this overlay holds to that same rule as strictly as the server side does — an earlier implementation here polled /api/ready every 400ms, which had a real failure mode (that fetch could itself stall behind the same congestion making the rest of the page unresponsive, so it could silently fail to appear exactly when needed most); this version can't fail that way because it depends on nothing but the clock. Fails open: if JS never runs (disabled, blocked, whatever), the overlay's default state is invisible and non-blocking — the page underneath is fully usable immediately. The overlay can only ever make a fresh cold start feel more confident; it can never lock anyone out of a working page. -#}
